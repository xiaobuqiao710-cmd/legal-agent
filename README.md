# legal-agent · 四智能体法律检索工作流

> 把「检索 → 分析 → 写作 → 质检」拆成四个职责单一的 Agent，用结构化消息协议串起来，
> 每一步产出在进入下一步之前都必须通过门禁校验；质检 Agent 拥有否决权，
> 且它的否决会**打回上一环节**而不是直接透传给用户。

这套东西存在的理由只有一个：**法律 AI 最不可接受的失败模式是编造与漏项，
而这两件事恰好都发生在"单次产出没人交叉复核"的地方。**

---

## 一分钟看懂它解决了什么

| 问题 | 单 Agent 的做法 | 本项目的做法 |
|---|---|---|
| 编造法条/案号 | 靠提示词叮嘱"不要编造" | 材料只能来自本地语料库，每条带 `locator`；分析引用不存在的材料 ID **在进入写作前就失败** |
| 漏掉核心争点 | 靠模型自觉 | 文档覆盖门禁 + 质检 C 类检查，漏项必被拦下 |
| 论证跳跃 | 无法程序化校验 | 每个争点必须挂 IRAC 四段 + 至少一条可核验引用，还带置信度 |
| 质检形同虚设 | 同一个模型自审 | 承办与对抗**异席位强制**（借鉴 sanjiu-core），且质检有真实否决权和回环 |
| 反复拉扯改不好 | 无限重试 | 硬计数熔断 + 修订版方案制（fix 必须可执行，空话被正则拦截） |

## 多 Agent 协作到底如何进行

这是本项目最想讲清楚的一件事。**多 Agent 协作的难点不在"让模型互相说话"，
而在四件工程上的事**，下面每条都对应代码里的一段真实实现。

### 一、Agent 之间传什么：结构化消息，不是自然语言

这是整个系统的地基。如果 A 对 B 说"我检索到几个相关案例"，B 无法判断
这是 3 个还是 30 个，也无法判断每个案例是否真的带案号 —— **自然语言无法被
下游程序化校验**。

所以本项目强制：每次流转传的是带字段的对象。

```
检索 Agent ──→ RetrievalResult {
  caseId, query,
  materials: [{ id, kind, source, locator, quote, relevance }],
  coverage, coreProvisionsInjected
}

分析 Agent ──→ AnalysisResult {
  caseId,
  issues: [{ id, question, rule, application, conclusion, cites[], confidence }]
}

写作 Agent ──→ DraftResult {
  caseId, title,
  sections: [{ issueId, heading, body, cites[] }]
}

质检 Agent ──→ QcResult {
  caseId, verdict: 'pass'|'revise'|'reject',
  findings: [{ severity, issueId, problem, fix }]
}
```

实现见 `lib/protocol.mjs`。校验器是手写的，**没有引入 ajv/zod** ——
字段很少且稳定，依赖越少别人越容易读懂并复用。

**一条关键设计：`locator` 不可为空。** 它把"不许编造法条"从提示词层面的
叮嘱，变成了结构层面的保证 —— 没有可核验定位符的材料根本进不了系统。

### 二、每步之间放什么：门禁，让错误不穿透

多 Agent 系统最常见的坏味道是"一个 Agent 错了，错误被下游一路放大"。
解法是在每一步之间放校验，**过不了就不许往下走**。

本项目有三道跨消息门禁：

| 门禁 | 位置 | 拦什么 |
|---|---|---|
| `validateRetrieval` | 检索 → 分析 | 材料缺 `source`/`locator`/`quote`；零结果却未声明原因 |
| `validateCitesResolve` | 分析 → 写作 | 论证引用了**检索结果里不存在**的材料 ID ← 这条拦"凭记忆编案号" |
| `validateDraftCoverage` | 写作 → 质检 | 文书漏写争点 / 出现多余章节 |

### 三、怎么分上下文：每个 Agent 只拿它该拿的

直接把上游**整份**消息丢给下游最省事，但会让下游注意力被用不到的字段稀释。
所以 `INPUT_SCHEMA` 做了显式投影：

- 分析 Agent **拿不到** `relevance` 分数 —— 那对论证没用，给了只会让它误以为
  "分数高 = 论证强"
- 写作 Agent 只拿争点的 IRAC 四段 + cites，拿不到检索原文
- **质检 Agent 反而拿全量** —— 它的职责就是交叉核对，少给字段等于让它无法发现那类错误

这个不对称是刻意的。

### 四、质检怎么才有意义：否决权 + 回环 + 熔断

**这是多 Agent 与"四个函数顺序调用"的分水岭。**

```
写作 → 质检 ──pass──→ 交付
        │
        ├─revise──→ 打回写作（带 feedback：具体改什么）──→ 再写 ──→ 再质检
        │                     ↑ 上限 MAX_REVISIONS = 2，超限熔断转人工
        │
        └─reject──→ 立即中止（材料不足以支撑，重写无用）
```

三个要点：

1. **feedback 必须带上"改什么"**。打回时把 `findings`（severity/issueId/problem/fix）
   一并交给写作 Agent，否则它只能盲改一遍碰运气。
2. **reject 与 revise 是两种不同的失败**。reject 意味着材料本身不足，
   重写只是换个说法 —— 所以立即中止，不浪费回环次数。
3. **超限必须如实输出，不能伪造通过**。状态是 `passed` / `rejected` /
   `escalated` / `revise_limit` / `no_materials`，没有"差不多算通过"。

### 五、怎么防止 Agent 自我审核：对抗式审计层

这部分借鉴自 [`silvrblt/sanjiu-core`](https://github.com/silvrblt/sanjiu-core)（三审九方）
的三条硬规则，针对四席位规模做了精简（见 `lib/audit.mjs`）。

| 规则 | 解决的失效模式 | 本项目的实现 |
|---|---|---|
| **异源强制** | 同一实现既写又审 → 自我检查系统性偏爱自己的产出 | `assertNonSelfAudit(producer, auditor)`，席位相同直接抛 `AUDIT_ERR_SAME_SEAT` |
| **硬计数熔断** | 反复微调把错误磨平，而非改对 | `AuditSession`：对抗≤2 / 裁决≤1 / 上诉≤1，超限熔断转人工 |
| **修订版方案制** | 只甩问题清单，两方来回拉扯 | `assertActionableFix`：fix 必须具体到"改哪段、改成什么"，空话被正则拦截 |

**与 sanjiu-core 的差异（诚实说明）**：席位 4 个而非 9 个；无 HMAC 回执闸门
（本项目是单进程内调用，回执机制无意义，若将来拆多进程应补）；
无 errors-ledger 跨案件持久化（当前只在 transcript 里留痕）。

## 引注核验器：为什么它是这个项目最值钱的部分

`tools/check-cites.mjs` 是一个独立能力，回答一个问题：
**「这段话里引用的法条，真的存在吗？」**

```
✅ 《证券法》第197条          → 归一为第一百九十七条，给出语料原文
❌ 《证券法》第九百九十九条    → 该法共收录 10 条，未收录第 999 条（列出已知条号）
➖ 《民法典》第五百零九条      → 超出本语料库覆盖范围（不静默放过）
```

**核心主张：LLM 只做抽取，判断完全确定性。**

抽取（把"《证券法》第八十五条"从文字里认出来）可以容忍不确定性；
判断（该条是否存在、内容是否相符）必须是可复现的确定性代码 ——
因为一旦让模型来判断"我引的对不对"，它就同时成了运动员和裁判员。

发现疑似编造时**退出码为 1**，可以直接接进 CI 或作为多 Agent 的独立门禁。

这个方向的选择有外部依据：2026-10-16 的 GitHub 实测调研显示，英文侧已把引注核验
证明为核心价值（`mike` 4348★ 内置 citation 核验、`korean-law-mcp` 2725★ 把引用核验
写进项目定位、Harvey LAB 1466★ 的 rubric 把"无出处即零分"写进评分标准），
**而中文侧这一层没有对应的开源项目**。

## 测试：为什么 52 项而不是几个

**一个"永远通过"的多 Agent 系统是没有价值的。**

所以测试的重点不是"链路能跑完"，而是**每一道门禁都真的会把人拦下来**。
每个门禁都用"故意注入的错误"测 —— 只有看着它把坏输入拦下，才能说这道门存在。

九组测试：

| 组 | 内容 |
|---|---|
| 一 | 端到端正向：CASE-001/002 跑通、引用可核验、材料可追溯 |
| 二 | 负向：无关案件必须 `no_materials`（**不硬凑条文**） |
| 三 | 协议门禁：注入缺字段/非法 kind/悬空引用 → 全部被拦 |
| 四 | 质检裁决自洽性：pass 不得带 findings 等 |
| 五 | 回环：revise 真的打回、超限不伪造通过、reject 不浪费回环 |
| 六 | fail-fast：错误不穿透 |
| 七 | 中文检索回归护栏（n-gram 分词不得退回恒零） |
| 八 | 引注核验器：真法条/编造/超范围/混合文本 |
| 九 | 审计层：异源强制、熔断、修订版方案、最后一轮配额 |

## 这套系统在建设过程中踩到的 11 个真实 bug

这部分本身就是"多 agent 协作如何进行"的实证答案 —— 下面每一个都是真实发生过、
被测试抓出来的缺陷，而不是设计设想。

### 检索与语料

**1. 中文检索恒零命中。** 原 `search()` 按空格/逗号切词，中文没有词间空格，
整句被当成一个 token，与语料里的"信息披露"永远无法子串匹配 → 5 个争点全部 0 命中。
表面上链路"跑通了"，实际产出完全不可用。
修法：`tokenizeCN()` 按标点切子句 + 2–4 字 n-gram 滑窗。

**2. 全局 top-N 截断导致静默漏项。** 各争点命中混排后取全局 top-10，
热度高的争点把责任主体条款 `S-85` 挤出榜单，分析 Agent 因缺材料而**静默跳过整个争点**
—— 程序不报错，但意见书漏掉一个核心问题。这比崩溃危险得多。
修法：按争点配额（每问 top-6），让每个争点都有自己的材料，谁也挤不掉谁。

**3. 通用二字词误召。** keywords 做了双向子串匹配，查询里出现"赔偿"，
任何引文含"赔偿"的材料都 +6 分 → 一个宅基地相邻关系纠纷召出 7 条证券法条文。
修法：≥3 字才允许模糊互含；2 字必须完全相等；且必须有"高信息量命中"。

**4. 关键词片段命中 ≠ 命中。** `当事人` 命中了关键词 `当事人承诺`，
又把无关案件召出两条处罚材料。判据：关键词是人工标注的**原子术语**，
命中它的片段不等于命中它。

**5. 核心条款落榜导致分析退化。** `S-78`（信息披露"真实准确完整"的基本要求）
因字面重合少而落榜，分析 Agent 只能输出"以检索所得信息披露规范作为定性依据"
这种没有指向的空话。
修法：`CORE_PROVISIONS` 保底表 + `collectCoreIds()`，把领域知识显式写下来 ——
判断"哪些条款是某类争点的核心依据"属于领域知识，不该交给字面相似度函数碰运气。

**6. 领域判据用了通用词。** 保底表的主题正则里写了"赔偿""程序"，
于是"精神损害赔偿"命中了投资者保护域。修法：领域判据必须用**有区分度**的术语
（先行赔付、代表人诉讼、当事人承诺、虚假陈述），排除普遍词。

### 编排与门禁

**7. 覆盖门禁遮蔽了回环机制（最有设计价值的一个）。**
`validateDraftCoverage` 在质检之前就硬抛，导致测试"revise 应打回重写"时
编排器直接抛错 —— **回环机制永远不可能被触发，是一段死代码**。
教训是一条通用分层原则：
> 结构性错误（缺字段、类型不对）→ 硬抛，因为下游无法处理；
> 内容质量问题（漏争点、论证太弱）→ 交给质检裁决，因为它**可被修复**。
> 把可修复的问题放进硬抛分支，等于取消了修复机会。

### 审计层

**8. reject 占用了对抗配额。** 初版让 reject 也走 `submitObjection` 再判断，
结果 reject 被记了一次对抗轮次。语义上 reject 是对**上游材料**的否决，
不该占用写作环节的对抗配额。修法：先判 reject 再计配额。

**9. 最后一轮配额被提前吃掉。** `if (remaining.objectionRounds === 0) return escalate`
导致配额刚好用满那一轮反而熔断，写作只被调用 2 次而非 3 次。
修法：能走到该行说明本轮打回是合法的（超限在上一层已 try/catch 转 escalate），
必须放行重写；剩余 0 只意味着"重写后仍不过就没有下一次了"。

**10. 空话词表用字面匹配。** `'建议加强'` 匹配不到「建议**进一步**加强该部分的论证力度」，
中文空话句常插入修饰词。修法：改正则，把修饰词做成可选段。

### 环境与工具

**11. CLI 入口判定在中文路径下恒为 false。**
`import.meta.url === \`file://${process.argv[1]}\`` —— 路径含「图鲲」时
`import.meta.url` 是百分号编码 `%E5%9B%BE%E9%B2%B2`，而 `argv[1]` 是原始 UTF-8，
两者永不相等 → CLI 静默不执行，**还返回退出码 0**。
这类"看起来跑成功了但什么都没做"的失败最难发现。
修法：`pathToFileURL(process.argv[1]).href` 比较。

## 局限（诚实说明）

1. **语料库只有 22 条，覆盖证券法/行政法/公司法三个领域。** 这是一个可运行的
   骨架与协议演示，不是能直接用于真实案件的法律数据库。要实用须接
   `flk.npc.gov.cn`（国家法律法规数据库）与人民法院案例库。
2. **四个 Agent 是确定性规则引擎，不是 LLM。** 这是刻意的：多 Agent 的难点在
   编排与协议，混入模型调用会让编排 bug 与模型不确定性纠缠；而且若四个 Agent
   都是 LLM，"质检是否真在挑错"就无从验证。
   接口已定死为 `input(结构化) -> output(结构化)`，接 LLM 只需替换这四个函数，
   编排器一行都不用改。
3. **无 HMAC 回执、无跨案件错误模式沉淀**（sanjiu-core 有，本项目按单进程场景省略）。
4. **不构成法律意见。** 产出物是工作底稿，必须由执业律师复核。
